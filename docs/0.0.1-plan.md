# Execução do primeiro lançamento 0.0.1

Status: núcleo técnico integrado em qualificação; lançamento externo bloqueado.

Data: 06/11/2026. Requisitos: [PRD](b3_prd.md) e [marcos G0–G7](prd_dev_milestones.md).

## Decisões aceitas

Primeiro contrato suportado, sem obrigações de compatibilidade com respostas, IDs ou ingestões anteriores. A persistência anterior pode ser descartada; nenhum descarte foi executado nesta entrega. Essa autorização é anterior ao lançamento e não permite apagar evidência nas reexecuções futuras.

O recorte é COTAHIST anual de 2025 e acumulado de 2026 até o corte demonstrado pelo corpus, mais sobreposições diárias/mensais disponíveis e fotografias cadastrais elegíveis. A data de corte não é o relógio da máquina. REST permanece em `/api/v1/b3`; MCP inicial é stdio. Famílias G6/G7 e preços ajustados ficam adiados.

## Implementação integrada e lacunas de qualificação

O runtime de release é conectado ao PostgreSQL e compartilha serviços entre API, worker, CLI e MCP. A cadeia contém migrations sequenciais `0001`–`0011`; a imagem do worker processa jobs duráveis por lane e a API registra comandos administrativos com `202 Accepted`. A elegibilidade é negada por padrão e avaliada por finalidade/canal antes de aquisição e consulta.

O fluxo de artefatos conserva conteúdo por SHA-256, inventaria ZIPs aninhados em ordem, preserva membros excluídos e limites agregados de expansão/metadados, e fornece readers para parsers incrementais. Parsers streaming cobertos incluem COTAHIST e os formatos de cadastro habilitados. O pipeline sintético prova staging, construção de candidato, publicação explícita, reparse, recuperação de lease expirada e recusa de worker obsoleto. Registry/TSL persistem os grupos tipados sem alterar valores históricos durante reconstrução de identidade.

As queries publicadas no contrato 0.0.1 suportam capabilities, cobertura, fatos/séries COTAHIST, snapshots de cadastro, detalhes de instrumentos, histórico de identificadores e Tradable Security List. REST e MCP compartilham queries; MCP usa processo real e papel PostgreSQL somente leitura em teste. Esses testes validam implementação e fixtures, não a disponibilidade, elegibilidade ou semântica completa de arquivos de produção.

Ainda precisam ser concluídos: revisão das chaves naturais contra corpus oficial; aceitação de fontes por finalidade e redistribuição sem custo obrigatório; corte e manifesto de corpus 2025–2026; calendário oficial versionado cobrindo o período; benchmark do corpus autorizado em ambiente de produção; e budgets derivados desse corpus. Os smoke da imagem corrente e o restore sintético seguido de leitura REST passaram, mas não substituem a qualificação final.

## Evidência exigida

Executar fmt, Clippy e testes completos através do serviço Compose `cargo`, usando PostgreSQL 16 isolado. Testes novos criam bases exclusivas e removem apenas essas bases. Não usar a base operacional para testar.

Os testes de aceitação sintética incluem HTTP simulado, artefatos aninhados, publicação concorrente por processos reais, execução do processo MCP com role read-only, discovery, staging de cadastro, correção/rollback e contratos REST/OpenAPI. O build/smoke, benchmark integrado e restore com 20.000 fatos sintéticos passaram, conforme [evidência operacional](release_operations.md). A ingestão de corpus oficial e os budgets de escala permanecem pendentes.

### Validação executada em 06/11/2026

- `docker compose run --rm cargo cargo fmt --all -- --check`: aprovado nesta revisão.
- `docker compose run --rm cargo cargo clippy --all-targets --all-features -- -D warnings`: aprovado nesta revisão, após encapsular o estado da recursão do inventário.
- `docker compose run --rm cargo cargo test --all-targets --all-features`: **65 testes aprovados, zero falhas e zero ignorados**, em PostgreSQL **16.15** usando `tucano_b3_test` isolado. Nenhum registro da base operacional `tucano_b3` foi usado para teste.
- Os testes incluem execução de dois workers em processos separados, MCP real com papel read-only, revisão/correção/rollback, TSL tipado, elegibilidade fechada, REST/OpenAPI e descoberta. Os testes criam/limpam bancos exclusivos onde necessário.
- `docker compose build b3_api b3_worker b3_migrate`: aprovado com código `0.0.1` validado. Em banco PostgreSQL 16.15 recém-criado: migrations `0001`–`0011` aplicaram; health/capabilities responderam 200; leitura sem permissão administrativa respondeu 403; worker executou um job pela fila; imagem API leu 100 fatos depois do restore.
- Benchmark reproduzível com 20.000 detalhes COTAHIST sintéticos: aquisição local 86 ms, inventário 40 ms, parsing+staging 21,581 s, tentativa total 21,802 s e publicação 43 ms. O worker teve RSS máximo amostrado de 5,93 MiB e CPU amostrada máxima de 8,5% (12 amostras desde o início); WAL do PostgreSQL isolado cresceu 45.880.583 bytes durante a ingestão. A API serviu 160 leituras concorrentes (8 workers, 100 itens por resposta), em 13,75 s: 11,64 req/s, p50 663 ms e p95 888 ms. O máximo amostrado da API foi 8,79 MiB; a contagem de clientes PostgreSQL chegou a 9, incluindo a conexão observadora. Banco após a publicação: 37.895.191 bytes; conteúdo raw endereçado: 4.920.492 bytes.
- Backup e restore do dataset de 20.000 fatos levaram 1,902 s e 2,387 s; revisão ativa e digest (`fc813955cada7569141c682bd5a9d92eb19b1569b23cf04046cfa1ad11ead50f`) foram idênticos, com 20.000 registros de referência e um raw restaurado. A API iniciou sobre o restore e retornou health 200 e 100 itens com proveniência.
- Esses valores são observações de uma fixture sintética em Docker Engine 29.8.2 (2 CPUs, 8 GiB, arm64), PostgreSQL 16.15, batch de 500 registros/4 MiB e limite padrão de 8 conexões. Não definem capacidade para arquivos reais, não medem rede B3 e não fixam budget de produção.
