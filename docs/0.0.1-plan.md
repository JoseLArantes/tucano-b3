# Execução do primeiro lançamento de plataforma 0.0.1

Status: qualificação técnica 0.0.1 concluída com PostgreSQL 16 e fixtures sintéticas; elegibilidade externa continua sendo um gate de ativação por canal, não do release da plataforma.

Data de revisão: 06/11/2026. Fonte de requisitos: [PRD único](b3_prd.md); situação dos marcos: [marcos de desenvolvimento](prd_dev_milestones.md).

## Decisões de lançamento

- `0.0.1` entrega a plataforma de aquisição, interpretação, persistência versionada, publicação, consulta e operação. Não exige que a equipe carregue um corpus de 2025–2026 nem que mantenha dados reais populando o ambiente de release.
- O banco e o namespace de raw de release começam vazios. Dados anteriores, IDs, estado de jobs e auditoria legados não são importados. Fixtures sintéticas ou autorizadas demonstram o comportamento e podem ser apagadas junto com um banco isolado.
- A fonte deve ser oficial da B3 ou relacionada e cadastrada por um administrador. Não existe upload de arquivos por usuário consumidor. Importação local é uma ferramenta operacional restrita a artefatos oficiais licitamente obtidos e preserva a mesma trilha, hash, manifesto e controles.
- Toda solicitação de import informa `from` e `to`. São limites inclusivos dos dados de negócio. Em COTAHIST, cada detalhe é selecionado por `DATA DO PREGÃO`; o ano ou período da publicação apenas ajuda a escolher os arquivos a adquirir. Para importar um ano completo, o administrador informa explicitamente o primeiro e o último dia.
- Artefatos anuais, mensais, diários ou acumulados que atendam a uma solicitação COTAHIST são reunidos em uma candidata e publicados como uma única revisão. Linhas fora do corte são contadas como `out_of_scope`; linhas dentro do corte são idempotentes por chave/hash de negócio.
- Import sem falha estrutural, rejeições ou conflitos é publicado automaticamente depois dos gates de qualidade. Candidato com rejeições ou conflitos permanece não publicado e termina `succeeded_with_issues`; não se escolhe silenciosamente uma versão divergente.
- Remoção é uma revisão lógica que retira datas da visão ativa. Raw, fatos/versões, ocorrências, auditoria e revisões anteriores permanecem para rollback e reimportação. Não há hard purge API; recriação completa fica restrita ao reset de ambiente isolado.
- A autorização para adquirir, reter, processar, servir REST/MCP e entregar a terceiros é registrada por fonte/canal/finalidade. Evidência pendente mantém aquele canal/finalidade desabilitado, mas não bloqueia implementação, testes sintéticos ou o release do software.
- Escopo inicial de conectores: COTAHIST anual/mensal/diário para fatos de mercado. BVBG.028 e Tradable Security List permanecem adiadas até que seus registros ofereçam uma referência de data interna adequada aos cortes do contrato; BVBG.086/186, BVBG.087, carteiras, ajustes de preços e integração CVM também ficam fora do primeiro conjunto operacional.

## Critérios de conclusão do software 0.0.1

1. Base PostgreSQL 16 vazia inicializa por migrations sequenciais; o teste de upgrade da versão anterior também passa sem reescrever migrations existentes.
2. Administrador submete import COTAHIST por intervalo e acompanha um job durável. API, CLI e worker usam os mesmos serviços; consumidor não pode enviar arquivos nem iniciar mutações.
3. O executor seleciona publicações por catálogo, valida a fonte/canal, mantém raw e members rastreáveis e filtra fatos pela data de negócio de cada registro dentro do intervalo inclusivo. Famílias sem esse dado não são aceitas para import.
4. Uma importação que usa múltiplos artefatos forma um resultado coerente. Repetição/reimportação não duplica fatos, versões ou auditoria; decisões de proveniência e revisão ficam rastreáveis.
5. Import limpo publica automaticamente. Falha, conflito, rejeição, cancelamento e worker obsoleto não substituem silenciosamente uma revisão ativa válida.
6. Administrador pode retirar logicamente um intervalo, observar a nova visão ativa e restaurar a versão anterior ou reimportar sem perder os dados imutáveis.
7. REST e MCP fornecem consultas COTAHIST e proveniência da mesma revisão, com auth separada, limites, cobertura e estado de identidade. Fatos sem vínculo cadastral permanecem `unresolved`; endpoints de cadastro/capacidades indicam que registro B3 está adiado neste release. Sem fonte ativa, a API informa indisponibilidade/cobertura vazia, sem fabricar histórico.
8. Testes sintéticos/permitidos em PostgreSQL real exercitam import de um dia e período, fontes sobrepostas, corte pela data do registro, idempotência após retirada/reimportação, publicação automática, qualidade degradada, falha, retry, rollback, auth e MCP read-only.
9. Build/smoke de API e worker, backup/restore, limites de recursos definidos por benchmark reprodutível e documentação descrevendo o comportamento entregue são concluídos.
10. A elegibilidade fail-closed está ativa: fonte/finalidade sem evidência não executa aquisição externa nem torna seus dados disponíveis a REST/MCP/terceiros.

## Política de ativação de dados

O [registro de elegibilidade](release_source_eligibility.md) responde se um canal específico pode ser usado para determinada finalidade. A existência de parser, endpoint, arquivo público ou URL oficial não substitui permissão para automatizar, reter, processar ou redistribuir.

Enquanto a evidência estiver pendente, o canal deve permanecer desabilitado para a finalidade correspondente. Engenharia e aceitação usam fixtures sintéticas ou amostras com uso autorizado. Ativar acesso externo a um canal é uma decisão operacional posterior e por canal; não muda os critérios do release de software.

## Evidências de qualificação técnica

Executadas em 06/11/2026 na árvore de trabalho desta entrega, sem dados oficiais externos:

- `docker compose run --rm cargo cargo fmt --all -- --check` — passou.
- `docker compose run --rm cargo cargo clippy --all-targets --all-features -- -D warnings` — passou.
- `docker compose run --rm cargo cargo test --all-targets --all-features` — 66 testes passaram com PostgreSQL 16.15 disponível; a execução não fez skip por ausência de banco.
- Migration upgrade `0011` → `0012` — passou em banco isolado: o histórico SQLx de `0001`–`0011` foi aplicado e o executável `tucano-b3 migrate` instalou `0012`; conferidos 12 registros de migration e as colunas de corte/contagem. O banco temporário foi removido.
- `npm --prefix docusaurus run build` — passou.
- `docker compose build b3_api b3_worker b3_migrate` — passou.
- Smoke com banco PostgreSQL isolado: API health/OpenAPI, capacidades com fontes de registro `deferred`, rejeição de job de ingestão dessas famílias sem criar job, e worker maintenance `--once` — passou.
- Benchmark sintético integrado e verificação backup/restore com consulta REST após restore — evidência e limites no [guia operacional](release_operations.md).

Não se executou aquisição ao vivo da B3 nem foi habilitada fonte externa. Esses passos exigem elegibilidade específica e não fazem parte da conclusão técnica do produto. O benchmark sintético é evidência de comportamento/recursos da plataforma, não homologação de arquivos oficiais nem budget de produção.

## Fora do critério de conclusão do software

- Importar qualquer corpus específico ou manter dados de mercado pré-carregados como condição para o release.
- Inferir um cutoff pela data atual do computador.
- Obter autorização para canais ou finalidade comercial em nome do mantenedor. Evidência inconclusiva mantém o canal inativo.
- Habilitar acesso automatizado à página COTAHIST enquanto a restrição aplicável não estiver resolvida. A página B3 atualmente publica um aviso de restrição à coleta automatizada; isso é tratado em [elegibilidade de fontes](release_source_eligibility.md), não contornado por um fornecedor intermediário.
- Prometer paridade com dados ou IDs do runtime antigo, preço ajustado, CVM, famílias G6/G7 ou MCP via HTTP.
